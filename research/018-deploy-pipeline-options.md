## 1. Adapter, netlify.toml, Node, env vars

- Adapter: `npx astro add netlify`; then `export const prerender = false` on the one page; default output stays `static`. Source: https://docs.astro.build/en/guides/on-demand-rendering/ ("By default, your entire Astro site will be prerendered ... add `export const prerender = false` ... The rest of your site will remain a static site"; tip: "Start with the default 'static' mode"). The adapter supports actions: "deploy your on-demand rendered routes and features ... including server islands, actions, and sessions" (https://docs.astro.build/en/guides/integrations-guide/netlify/, v8.2.14 shown).
- Adapter options for the build ticket: `imageCDN` (default on, Netlify Image CDN), `staticHeaders` (default false; writes Astro-provided static headers such as CSP into Netlify config), `middlewareMode`, `devFeatures`, and `session: false` to drop the Netlify Blobs session runtime (010 says no sessions). Same page.
- Skew protection: the adapter injects the deploy ID into actions requests automatically (same page), so an old page's form post goes to its own deploy during a switch.
- Minimal `netlify.toml` (https://docs.astro.build/en/guides/deploy/netlify/): `[build] command = "npm run build"  publish = "dist"`. `netlify.toml` overrides UI settings (https://docs.netlify.com/build/configure-builds/file-based-configuration/: "settings specified in `netlify.toml` override any corresponding settings in the Netlify UI").
- Context overrides: `[context.production]`, `[context.deploy-preview]`, `[context.branch-deploy]`, `[context.<branch>]` (most specific wins); `[[headers]]` and `[[redirects]]` are not context-aware. Same page. A `v2`-specific build command is possible with `[context.v2]`.
- Node pin: `.nvmrc` or `.node-version` in the base directory, or a `NODE_VERSION` env var; these override the UI setting; `netlify.toml` is **not** a documented way to set Node (https://docs.netlify.com/build/configure-builds/manage-dependencies/). Netlify pins a site to the image default at creation. Astro's Netlify guide: "Astro requires `v22.23.4` or higher" (as printed; check against Astro's current `engines`). Option: `.nvmrc` plus `engines` in `package.json`, with `actions/setup-node` reading the same `.nvmrc` so CI and Netlify agree.
- **Env var scoping conflicts with ticket 015.** Netlify: "Scopes are available on the Pro plan and above" (https://docs.netlify.com/build/functions/environment-variables/) and "Scopes (available on Pro and Enterprise plans)" (https://docs.netlify.com/build/environment-variables/overview/). The Free plan cannot restrict the Resend key to the Functions scope; an unscoped variable is available to all scopes, including Builds. Also "Environment variables declared in `netlify.toml` are not available to serverless functions", so the key goes in UI/CLI/API, never in the file. Options: (a) accept all-scopes on Free and keep the key out of every bundle with Astro `astro:env`: `envField.string({ context: "server", access: "secret" })`, which "are not part of your final bundle" (https://docs.astro.build/en/guides/environment-variables/); (b) upgrade to a paid plan for scoping (cost; 015 says no paid plans); (c) "Contains secret values" (https://docs.netlify.com/build/environment-variables/secrets-controller/): Free availability UNVERIFIED, and one Free-plan forum report says flagged vars were undefined in Functions runtime (https://answers.netlify.com/t/env-vars-flagged-contains-secret-values-not-injected-into-functions-runtime-process-env-non-secret-vars-work-fine-same-deploy/167922; single secondary source, UNVERIFIED). Astro validates secrets at runtime by default; `env.validateSecrets: true` validates at build and "is useful in some continuous integration (CI) pipelines", but then CI and the Netlify build need the variable or a dummy (https://docs.astro.build/en/reference/configuration-reference/#envvalidatesecrets).
- Values can differ per deploy context (Production, Deploy Previews, Branch deploys, a branch value such as `release/*`) (overview page above). Option: leave the Resend key unset on Deploy Previews so previews cannot send mail; the form then takes the 010 fallback path. Env changes apply on the next deploy (functions page: "applied based on the values set at the time of deployment").

## 2. Previews and branch deploys

- Terms (https://docs.netlify.com/deploy/deploy-overview/): the production branch deploys to the main URL; branch deploys go to `<branch>--site.netlify.app` (`staging--mysitename.netlify.app`); Deploy Previews come from pull requests (`deploy-preview-42--site.netlify.app`); permalinks `<deployid>--site.netlify.app` never change.
- Which branches deploy: Project configuration > Developer settings > Continuous deployment > Branches and deploy contexts: individual branches (wildcards such as `features/*`), All, or None. "All" excludes the production branch. Same page.
- For this repo, v1 stays on `production` untouched. Option A: add `v2` as a branch deploy (always-on `v2--jpsantos.netlify.app`, one URL for the owner's audits). Option B: no branch deploy, PR previews only (needs a PR from `v2`). Option C: both. A PR preview can be skipped with `[skip ci]` or `[skip netlify]` in the title (from a search summary of Netlify docs, UNVERIFIED; check before relying on it).
- Cost: on credit plans "Deploy Previews and branch deploys cost 0 credits" (https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/). On the legacy Free plan, builds use the 300 build minutes, previews included (inference, UNVERIFIED).
- Not researched: protecting preview URLs on Free, and `noindex` on non-production contexts (build ticket).

## 3. Where `npm run check` runs and how failure blocks a deploy

Netlify limits, legacy Free: 300 build minutes/month hard limit; 100 GB bandwidth/month hard limit; 125k serverless invocations per site/month; 1M edge invocations (legacy pricing page, link above). Credit-based Free: 300 credits/month, hard limit, "Production deploys consume 15 credits" (20 production deploys/month), previews free, "Failed deploys and rolling back a production deploy ... does not consume credits", and at zero "all of your web projects ... are paused and visitors ... will find a `Site not available` page" (credit pages above). The pool is team-wide: 6 sites share it.

GitHub Actions: the repo is public, and "Standard GitHub-hosted runners in public repositories" are free (https://docs.github.com/en/billing/concepts/product-billing/github-actions). A private repo would draw on the $12/month included compute (Linux 2-core $0.006/min), so going private would change this.

Playwright on CI: its page uses `ubuntu-latest` and `npx playwright install --with-deps`, says "operating system dependencies need to be installed, which are not cacheable" and "Caching browser binaries is not recommended", and suggests `workers: 1` on CI (https://playwright.dev/docs/ci). LHCI: `lhci autorun`, `collect.staticDistDir`, 3 runs by default, assertions as `resource-summary:<type>:(size|count)` with `maxNumericValue`; an `error` assertion gives a non-zero exit code, `warn` does not (https://googlechrome.github.io/lighthouse-ci/docs/configuration.html). Whether `resource-summary` sizes are transfer (gzipped) or raw bytes was not established, UNVERIFIED, and matters because 007's budgets are gzipped. With the adapter, `staticDistDir` would miss the on-demand Contact page; `startServerCommand` against `npm run preview` is the likely route (inference, UNVERIFIED).

Options:
- **A. GitHub Actions runs `npm run check`; Netlify only builds.** Protect `production` with a required check so changes arrive only by passing PR. Pros: free minutes, all three browsers on a runner with deps, no Netlify minutes beyond the build. Cons: protections "don't apply to repository admins" unless "Do not allow bypassing" is set (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), so the owner can still push straight to `production`; the check tests the PR head, and the Netlify build on the merge commit is not re-checked unless "Require branches to be up to date" is on.
- **B. Run `npm run check` in the Netlify build command.** Non-zero exit fails the build; a failed build should leave the published deploy in place (standard behaviour, page not fetched, UNVERIFIED). Pros: hard gate on the real deploy path. Cons: spends scarce shared build minutes (Playwright x3 plus LHCI); Playwright browsers and OS deps on Netlify's build image not verified (UNVERIFIED); build and tests share one machine, and the on-demand page needs a preview server.
- **C. Actions checks, then Actions deploys with the Netlify CLI, Netlify auto builds stopped.** `netlify deploy --prod` needs `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID` (https://docs.netlify.com/api-and-cli-guides/cli-guides/get-started-with-cli/); the Astro adapter docs describe building locally then running `netlify deploy`. Pros: deploy strictly after green checks; no Netlify build minutes. Cons: more moving parts, a token secret in GitHub, loses Netlify PR previews and statuses; `--no-build` and billing treatment of CLI deploys are undocumented in the pages read (UNVERIFIED); function bundling via CLI needs a trial.
- **D. A plus a Netlify `ignore` guard.** `[build] ignore = "..."`: "An exit code of `1` ... the build process continues ... `0` ... the build should stop" (https://docs.netlify.com/build/configure-builds/ignore-builds/); it does not cancel build-hook builds. Could skip builds of unchecked commits.
- Netlify commit statuses on PRs are on by default for GitHub sites (https://docs.netlify.com/deploy/deploy-notifications/). A `deploy/netlify` check can be required, but older forum threads report it hanging; the preview-specific check was the workaround (secondary, UNVERIFIED). It proves the build only, not the quality bar.
- Rulesets vs classic protection: GitHub's rulesets page says rulesets are "for customers on GitHub Team and GitHub Enterprise plans" and does not mention public repos on Free (https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets). Availability of rulesets and of required checks for this public Free repo is UNVERIFIED; the owner can test in Settings.
- Split option: fast gates (ESLint, Prettier, Stylelint, `astro check`, Vitest, html-validate) on every push; Playwright x3, axe and LHCI on PRs into `production`. Runner time is free on a public repo, so the split is for speed.

## 4. Replacing v1 with v2 on `production`, and rollback

- Rollback: "Use the **Publish Deploy** button on the detail page of any successful deploy. This doesn't trigger a new deploy but instead publishes a previous atomic deploy ... Rollbacks are instantaneous." But "any new Git-triggered production deploys will overwrite the previously rolled back version" (https://docs.netlify.com/deploy/manage-deploys/manage-deploys-overview/). To hold a rollback, **Lock to stop auto publishing** in the Deploys list (new deploys are still built but not published); **Unlock to start auto publishing** reverses it. Rollback costs 0 credits on credit plans.
- Retention: deploys are deleted after 30 days (90 on paid), except the published deploy, the latest successful production deploy and the latest successful branch deploy per branch. Same page. So v1's last production deploy is deleted about 30 days after v2 replaces it, and later rollback to v1 needs a rebuild from tag `v1` (whether v1's webpack build still runs on the current image is UNVERIFIED).
- Functions on rollback: the docs do not say whether functions, env vars and forms roll back with a deploy: UNVERIFIED. A rollback to a v1 deploy is static anyway.
- Git strategies (v1 frozen at tag `v1`, per AGENTS.md):
  - **G1 Merge `v2` into `production`** (PR). No force push, history intact; if v2 was started from scratch, unrelated histories may need `--allow-unrelated-histories`; v1 files show as one large deletion.
  - **G2 Reset `production` to `v2`** (force push). Clean history, v1 reachable via tag `v1`. Needs the owner's go; conflicts with branch protection; undoing needs another force push.
  - **G3 Re-point Netlify's production branch** to `main` or `v2` in the UI, leaving `production` as frozen v1. Switching back is the rollback, but AGENTS.md defines `production` as the deploy branch, so docs and habits change.
  - **G4 Lock-then-publish cutover** (works with G1 or G2): lock the v1 deploy, push v2 to `production`, Netlify builds v2 without publishing it, test the unpublished deploy at its permalink (`<deployid>--jpsantos.netlify.app`) with production env and the owner's launch audit (007), then Publish Deploy; rollback is Publish Deploy on the v1 deploy while still inside retention. Pros: v2 is verified on production config before any visitor; instant undo. Cons: manual UI steps; remember to unlock.
- DNS: `jpsantos.eu` is on Netlify DNS (vault 010, as of 2026-11-15), so no DNS change is needed for the cutover. Email DNS is 015's.
- v1 URL redirects: ticket 023. The adapter can emit `_redirects` from Astro `redirects` config (adapter page).
